# Work return delivery

Normal publication uses one stable Core job, `agent_work.return:<childRunId>`, scheduled from committed child admission and terminal transitions. Repeated scheduling reuses that job. A retained notice completes publication; the existing consumer handles coordination admission separately. Unfinished or currently unbound children yield with the configured lifecycle recheck delay, without consuming failure retries. Dependency failures use existing Core retry/backoff and dead-letter handling. The return adapter uses the existing lifecycle producer retry budget of ten; this change adds no retry framework.

A dead-lettered stable job remains dead-lettered: scheduling disposition `existing` does not revive it. Generic Core DLQ replay creates a different job identity and idempotency key and is not supported by this strictly bound adapter. Recovery uses the existing internal materialization operation: an administrator submits `/internal/agent-work/returns/materialize` with schema `workspace.agent_work.return_materialize.v1` and the original child `workAgentRunId`. The operation derives the outcome from authoritative committed facts and retains one idempotent notice. Repeating it returns the same notice; it neither starts another child nor runs a model. A `pending` result requires the authoritative outcome to become available before retrying. Source records and the original dead letter remain retained.

The shared audit repairs missed scheduling. Configure `WORK_RETURN_AUDIT_INTERVAL_SECONDS` explicitly for the deployment: it is the delay between pages, not a guarantee for a whole pass. Claiming a page durably spends that interval, even if the response or finish request is lost. The page contains at most 100 source rows. Delivered rows need no materialization or enqueue request. A durable frozen upper cursor and a shared fenced lease preserve restart progress and prevent replicas from duplicating the same page. Each lease covers two configured HTTP control deadlines: claim transport and one worker round. Worker calls share one remaining deadline, reserving its final fifth for the cursor finish request.

For N historical rows, a successful full-page pass requires at least ceil(N/100) pages. Its elapsed time includes those page delays, HTTP processing and the five-second control wake cadence. Partial pages require more rounds; unavailable dependencies can delay completion further. A missed source behind the current cursor is visited on the next pass, so late additions may wait through the remainder of one pass plus the following pass. Choose the interval against this repair lag and deployment history size. Normal jobs do not wait for this audit interval; an already pending job follows its configured recheck delay.

Unknown scheduling results, missing sources and authentication failures retain the preceding cursor. Idempotent scheduling retries resolve lost responses. The exact `agent_work_return_binding_rejected` rejection is recorded and does not block later sources; its authoritative source remains available for the next whole pass. Audit completion cannot discard source sessions or return notices.

Migration `0012_work_return_audit` follows `0011_upload_capacity` and adds only audit progress state. Existing work sessions, outcomes and notices remain authoritative and enter the first bounded pass. The final migration graph must have a single leaf when the upload parent is combined.
